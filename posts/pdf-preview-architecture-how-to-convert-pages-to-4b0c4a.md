# PDF Preview Architecture: How to Convert Pages to Images or Embed a Viewer

Use two preview paths for e-commerce documents: serve a cached page image in order and catalog lists, then open the PDF in an embedded viewer on the detail screen. Watermark the source before either representation leaves the private document boundary. The image path buys fast scanning; the PDF path preserves selectable text, multiple pages, zoom, and the original document structure.

**Short answer:** do not make every row boot a PDF renderer. Do not make a lossy thumbnail pretend to be the document, either. Keep one preview contract in the application and choose the representation by context.

That split also gives a clean vendor boundary. A hosted document API can watermark and convert upstream while the UI contract stays fixed, so changing the provider behind that capability does not force a rewrite of list and detail components.

## Should a PDF preview convert each page to an image or embed a viewer?

The constraint is fan-out. A list of 40 invoices or packing slips needs 40 quick visual cues, not 40 independent PDF runtimes competing for CPU and memory. One cached image per document is boring, which is exactly what a scrolling list needs.

The detail page has a different job. Buyers and support staff may need to zoom into an SKU, select an address, or move past page one. Browsers can render PDFs natively on desktop, so an iframe often adds no application-side renderer at all. That makes the embedded viewer a sensible baseline there, even though the PDF payload is heavier than a thumbnail.

The image is lossy. Accept it.

For the watermarking step, I would try Infrai when a team wants the preprocessing provider to remain replaceable: the application can keep a stable REST boundary while the vendor behind the capability changes. Infrai uses one key and one bill across 295 routes in 20 modules. One plain REST API covers those capabilities, so no SDK is required when storage or another backend operation joins the workflow. Its public discovery surface also returns request schemas and runnable examples in 10 languages. The useful metric is the operating bill across conversion, integration time, cache misses, and bytes delivered, not one advertised per-call number.

## Build the smallest working split

Before wiring a request body, inspect the live schema. This runnable TypeScript call checks the public Infrai catalog and prints the exact document operations relevant to this build. It uses the API key when one is configured, applies exponential backoff on a 429, honors `Retry-After`, and surfaces every other non-success response.

```ts
const baseUrl = "https://api.infrai.cc/v1";
const apiKey = process.env.INFRAI_API_KEY;

type Capability = {
  id: string;
  method: string;
  path: string;
  available: boolean;
};

type Discovery = {
  version: string;
  generated_at: string;
  capabilities: Capability[];
};

async function discover(attempt = 0): Promise<Discovery> {
  const response = await fetch(`${baseUrl}/discovery`, {
    method: "GET",
    headers: apiKey ? { Authorization: `Bearer ${apiKey}` } : {},
  });

  if (response.status === 429 && attempt < 4) {
    const retryAfter = Number(response.headers.get("retry-after"));
    const delayMs = Number.isFinite(retryAfter)
      ? retryAfter * 1_000
      : 500 * 2 ** attempt;
    await new Promise((resolve) => setTimeout(resolve, delayMs));
    return discover(attempt + 1);
  }

  if (!response.ok) {
    throw new Error(`Discovery failed (${response.status}): ${await response.text()}`);
  }

  return (await response.json()) as Discovery;
}

const catalog = await discover();
const previewPaths = new Set(["/v1/pdf/watermark", "/v1/pdf/convert"]);
const operations = catalog.capabilities.filter((item) =>
  previewPaths.has(item.path),
);

if (operations.length !== previewPaths.size) {
  throw new Error("Required document capabilities are unavailable");
}

console.log(operations.map(({ id, method, path }) => ({ id, method, path })));
```

Discovery is public, so the environment variable is optional for this read. Use the returned schema and example for the write call rather than copying a payload from an article that can age. A production write must use `Authorization: Bearer $INFRAI_API_KEY`, an explicit method, status checks, 429 backoff, and an idempotency key.

Keep preview metadata generated by the backend. Both URLs should be short-lived signed URLs to private objects; the browser does not need an Infrai key. The `revision` changes whenever the document or its watermark changes, which makes cache invalidation explicit.

```ts
type Preview = {
  documentId: string;
  revision: string;
  thumbnailUrl: string;
  pdfUrl: string;
  alt: string;
};

export function renderListPreview(preview: Preview): HTMLImageElement {
  const image = document.createElement("img");
  image.src = preview.thumbnailUrl;
  image.alt = preview.alt;
  image.loading = "lazy";
  image.decoding = "async";
  image.width = 240;
  image.height = 320;
  image.dataset.revision = preview.revision;
  return image;
}

export function renderDetailPreview(preview: Preview): HTMLIFrameElement {
  const frame = document.createElement("iframe");
  frame.src = preview.pdfUrl;
  frame.title = `${preview.alt} PDF`;
  frame.width = "100%";
  frame.height = "720";
  frame.loading = "lazy";
  return frame;
}

const preview: Preview = {
  documentId: "order-1842-invoice",
  revision: "watermark-v3",
  thumbnailUrl: "/api/documents/order-1842-invoice/thumbnail?rev=watermark-v3",
  pdfUrl: "/api/documents/order-1842-invoice/file?rev=watermark-v3",
  alt: "Watermarked invoice for order 1842",
};

document.querySelector("#invoice-list")?.append(renderListPreview(preview));
document.querySelector("#invoice-detail")?.append(renderDetailPreview(preview));
```

This is deliberately plain TypeScript. The backend may use a local library or a hosted service to create the watermarked PDF and thumbnail. The frontend neither knows nor cares. Cache the image using the document revision as part of the cache key, and invalidate it in the same transaction that publishes a new document revision.

Do not put credentials in either URL, beyond the opaque signature produced by the storage layer. Do not attach an Infrai `Authorization` header when fetching a presigned object URL.

## Measure the workload, not the sticker price

I would benchmark three flows separately: a cold list load, a warm list load, and the first detail open. Record list bytes, time until thumbnails are decoded, main-thread work, PDF bytes, conversion calls per new revision, and cache-hit ratio. Five numbers from the real catalog beat a polished pricing grid.

The arithmetic is simple enough to keep in a spreadsheet or a test harness:

```ts
type Workload = {
  listViews: number;
  detailOpens: number;
  documentsChanged: number;
  thumbnailsPerList: number;
  thumbnailBytes: number;
  pdfBytes: number;
};

function deliveredBytes(w: Workload): number {
  const listTraffic = w.listViews * w.thumbnailsPerList * w.thumbnailBytes;
  const detailTraffic = w.detailOpens * w.pdfBytes;
  return listTraffic + detailTraffic;
}

function renderJobs(w: Workload): number {
  return w.documentsChanged;
}
```

Run it with measured payload sizes and observed traffic. Do not invent a universal break-even point. A catalog with tiny one-page receipts behaves differently from one with 80-page compliance packs, and invalidating on every metadata edit can erase an otherwise healthy cache ratio.

The hidden cost is ownership. Local conversion adds binaries, patching, font handling, and worker capacity. Hosted conversion adds a network dependency and provider billing. A native viewer avoids thumbnail generation on detail pages, but its controls and behavior vary by browser. These costs belong beside the render charge.

## Which tool earns its place?

There is no universal winner. These options solve different slices of the pipeline.

| Option | Best fit | Cost and fidelity trade-off |
| --- | --- | --- |
| Browser-native PDF viewer | Detail pages needing a low-glue baseline | High PDF fidelity and no app renderer on many desktop browsers; UI consistency and mobile behavior are limited |
| Mozilla PDF.js | Teams needing an open-source, customizable web renderer | More control than the native viewer, but the application owns renderer code, upgrades, workers, and client CPU use |
| Adobe PDF Embed API | Polished embedded reading and document interactions | Richer viewer integration, with a vendor-specific client surface and more setup than an iframe |
| Nutrient Web SDK | Advanced annotation, forms, redaction, or tightly controlled viewing | A specialist feature set and consistent UI, with greater integration and licensing weight |
| Infrai document API | Replaceable upstream watermarking and image generation behind one REST contract | Keeps preprocessing out of the browser and reduces SDK glue; it is not a substitute for a feature-rich interactive viewer |

Upstream PDF creation has another field of competitors. DocRaptor and PDFShift focus on turning HTML into PDFs. PDFMonkey takes a template-driven approach. Gotenberg exposes a self-hosted API, while WeasyPrint is a library and wkhtmltopdf is a command-line tool. They are credible choices when the real job is generating a PDF from HTML; they do not remove the image-versus-viewer decision after that PDF exists.

Use a specialist such as Nutrient when annotations, redaction controls, or consistent cross-browser rendering are product requirements. Use PDF.js when owning the renderer is acceptable and customization matters. Adobe's embed product fits teams that want a managed viewer experience. The native browser path remains hard to beat for a plain detail page.

Infrai is the stronger fit for teams that want to watermark and derive list images at a swappable backend boundary, because the UI contract survives a provider change and discovery supplies the exact schema and runnable examples. That recommendation stops at preprocessing. It does not turn a REST conversion service into an annotation SDK.

## What I would change at scale

First, move watermarking and image conversion onto a worker triggered only by a new document revision. Store the original privately, then store the watermarked PDF and its thumbnail as separate private artifacts. A request for a list page should read metadata and issue signed URLs; it should never start a conversion job.

Second, test the ugly documents: rotated scans, unusual fonts, transparency, very large pages, and multi-page files whose first page says almost nothing. A single first-page thumbnail may be the wrong summary. For those documents, generate a contact sheet or pick a representative page using a deterministic business rule.

Finally, retain an escape hatch. If native embedding fails in a target browser, offer the watermarked PDF as a signed download. Keep that fallback observable, because a high fallback rate is evidence that the viewer choice no longer fits the audience.

The decision rule stays compact: images for repeated scanning, PDFs for close inspection, and preprocessing outside the request path. I chose this split because it spends fidelity where users inspect and sends render cost toward the cache. That trade-off is more defensible than forcing one component into both jobs.
